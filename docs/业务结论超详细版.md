# Olist 电商经营诊断业务结论超详细版

记录日期：2026-09-23

## 0. 文档说明

这份文档用于解释整个项目的分析逻辑、指标口径、关键结果和业务建议。它不是看板截图说明，而是一份可以从数据源、SQL、Python、Power BI 一直讲到业务行动的分析报告。

读者可以是：

- 项目作者本人，用于复盘和面试准备
- 面试官，用于判断分析过程是否可信
- 运营、客服、履约或卖家管理同学，用于理解看板应该怎么用

## 1. 项目目标

Olist 是一个巴西电商平台数据集。本项目要回答四个问题：

1. 平台收入主要来自哪里，收入是否有明显波动？
2. 哪些地区、类目和卖家存在履约和评价风险？
3. 客户是否会复购，复购客户有什么特征？
4. 针对收入、履约和客户价值，运营下一步应该优先做什么？

对应到 Power BI 五页看板：

| 页面 | 核心问题 | 主要决策 |
|---|---|---|
| 经营总览 | 整体经营是否健康 | 看 GMV、订单、客单价、复购、延迟、差评 |
| 类目与地区 | 收入来自哪里，风险在哪里 | 类目和地区资源分配 |
| 履约与评价 | 延迟和差评如何产生 | 预计送达校准、卖家/承运治理 |
| 客户经营 | 客户是否留下来 | 召回、复购实验、客户分层 |
| 卖家风险 | 哪些卖家需要优先检查 | 抽查、整改、限流或淘汰 |

## 2. 数据范围

### 2.1 原始数据

数据来源是 Kaggle/和鲸可获取的 Brazilian E-Commerce Public Dataset by Olist，约 10 万订单、9 张表。

| order_payments | 支付方式和支付金额 |
| order_reviews | 评价分数和评价时间 |
| products | 商品属性、类目原始名称 |
| product_category_translation | 类目英文翻译 |
| sellers | 卖家州和城市 |
| geolocation | 地理位置信息 |

原始 CSV 已导入本机 MySQL，项目不要求重新下载或重建数据库。GitHub 仓库只保存代码、SQL、文档和报表源码，不保存原始 CSV。

## 4. 分析视图设计

直接在原始表上分析会遇到订单一对多问题：一个订单可以有多件商品、多个卖家、多笔支付和多条评价。如果不先聚合，会重复计算 GMV 或订单量。

因此项目建立了两层分析视图：

### 4.1 基础分析视图

| 视图 | 粒度 | 用途 |
|---|---|---|
| v_order_analytics | 一行一个订单 | 经营、履约、评价、地区 |
| v_customer_analytics | 一行一个 customer_unique_id | 复购、客户价值、RFM |

### 4.2 Power BI 支持视图

| 视图 | 粒度 | 用途 |
|---|---|---|
| v_order_item_analytics | 一行一个商品行 | 类目、地区、卖家交叉分析 |
| v_category_analytics | 一行一个类目 | 类目销售和风险 |
| v_seller_risk_analytics | 一行一个卖家 | 卖家规模和风险分层 |

### 4.3 为什么不能直接算

如果一个订单有 3 件商品，直接在订单表与商品表连接后求和，订单金额可能被计算 3 次。解决方法是先按订单聚合支付金额、履约天数和评价分数，再连接维度表。

## 5. 指标口径详细说明

### 5.1 GMV

口径：已送达订单的支付金额求和。

特殊处理：仅有 1 笔已送达订单没有支付记录，商品金额为 143.46 BRL，因此使用商品金额加运费兜底，同时保留原始支付字段用于审计。

DAX 等价逻辑：CALCULATE(SUM(recognized_gmv), is_delivered = 1)。

### 5.2 成交订单量

口径：已送达订单去重计数。由于订单视图本身已是订单粒度，因此统计结果为 96,478。

### 5.3 客单价

口径：GMV / 成交订单量。结果为 15,422,605.23 / 96,478 = 159.86 BRL。

该指标受高金额订单和类目结构影响，不能单独代表客户价值。

### 5.4 复购客户和复购率

复购客户：至少 2 笔已送达订单的 customer_unique_id。

复购客户率：复购客户数 / 成交客户数。

结果：2,801 / 93,358 = 3.00%。

注意：不能使用 customer_id 判断复购，因为同一自然人下不同订单会得到不同 customer_id。

### 5.5 履约指标

| 指标 | 公式 |
|---|---|
| 支付审核天数 | 订单审核时间 - 下单时间 |
| 卖家处理天数 | 交付承运时间 - 订单审核时间 |
| 运输配送天数 | 客户签收时间 - 交付承运时间 |
| 总履约天数 | 客户签收时间 - 下单时间 |
| 预计送达偏差 | 客户签收时间 - 预计送达时间 |
| 延迟订单 | 客户签收时间晚于预计送达时间 |

延迟率分母只包含同时有实际送达和预计送达时间的已送达订单。

### 5.6 评价指标

差评订单：同一订单所有评价中的最低评分 <= 2。

差评率分母：有评价记录的已送达订单。未评价订单不进入分母，因为“未评价”不代表满意。

### 5.7 卖家风险指标

卖家 GMV：该卖家参与的所有已送达订单商品金额加运费。
卖家成交订单数：该卖家参与的已送达订单去重计数。
卖家延迟率：该卖家的延迟订单数 / 有履约日期订单数。
卖家差评率：该卖家的差评订单数 / 有评价订单数。

## 7. 收入趋势分析

2017-11 GMV 达到 1,153,528.05 BRL，是观察期最高单月。2018 年多数月份稳定在约 100 万 BRL，但未继续突破 2017-11 峰值。

业务解释：

- 2017-11 可能受黑五或促销影响，属于季节性峰值。
- 2018 年缺乏新的峰值，说明收入增长可能进入平台期，也可能受数据观察期限制。
- 2016 年样本较少，不能用于判断长期趋势。

- 卖家至少有 200 笔已送达订单。
- 延迟率 >= 12% 或差评率 >= 18% 进入观察。
- 延迟率 >= 12% 且差评率 >= 18% 为高风险。

## 13. 业务建议

### 13.1 履约治理

1. 对 RJ、BA、CE、MA、AL 校准预计送达时间。
2. 对延迟超过 4 天的订单建立预警和主动客服。
3. 把卖家处理、承运配送和预计偏差拆开考核。
4. 对连续延迟地区重新评估承运商。

### 13.2 类目治理

1. 对 bed_bath_table、office_furniture、watches_gifts 下钻卖家。
2. 不因类目均值高就忽略个体卖家问题。
3. 对高运费、高差评类目检查包装、破损和描述一致性。

### 13.3 客户经营

1. 对高消费待激活客户在 28 天和 80 天窗口测试召回。
2. 对高价值流失风险客户做低频高质量触达。
3. 用 A/B 测试验证召回优惠、推荐和复购提醒。
4. 评估增量 GMV，而不是只看消息打开率。

### 13.4 卖家治理

1. 先抽查订单，不直接淘汰。
2. 要求 30 天整改并监控延迟率和差评率。
3. 整改无改善再限流，最后才考虑淘汰。
4. 对高 GMV 风险卖家设置专人跟进。

## 14. 监控方案

| 频率 | 指标 | 告警建议 |
|---|---|---|
| 日 | GMV、成交订单、延迟订单 | 异常波动或延迟集中上升 |
| 周 | 地区延迟率、卖家处理天数、承运配送天数 | 延迟率 > 12% |
| 周 | 差评率、差评订单量 | 差评率 > 18% |
| 月 | 复购客户率、高消费待激活人数 | 召回后复购率无改善 |
| 月 | 风险卖家数、风险卖家 GMV | 风险卖家 GMV 上升 |

## 15. 数据限制和不能下的结论

- 不能计算利润，因为缺少成本和利润字段。
- 不能计算完整漏斗，因为缺少浏览、加购和访问行为。
- 不能证明延迟导致差评，只能说明两者高度相关。
- 不能把类目 GMV 相加得到平台 GMV。
- 不能忽略促销季对 2017-11 峰值的影响。
- 不能把同一自然日复购的 0 天间隔直接当作真实复购行为。

## 16. 如果面试官追问

### 为什么不用所有订单计算 GMV？
因为取消、未完成和异常订单不代表最终成交，会高估收入。统一用 delivered 才能和复购、履约和评价口径一致。

### 为什么复购率这么低还要分析？
低复购本身就是一个重要经营结论。它说明平台增长更依赖获客，同时高消费待激活人群仍提供有限的存量增长机会。

### 如何证明卖家风险不是误判？
通过至少 200 笔订单的门槛降低小样本波动，并同时看延迟率、差评率、GMV 和订单量。最终建议先抽查和整改，不直接淘汰。

### 为什么建议延迟 4 天作为阈值？
因为延迟 1 至 3 天差评率约 19%，延迟 4 至 7 天跳升到 61.31%，说明 4 天是体验恶化的明显分界点。

### 这个项目最有价值的分析是什么？
把收入、履约、客户和卖家放到统一成交口径下，发现收入集中、履约分层和低复购并存，并给出按优先级执行的治理顺序。

## 17. 最终结论

1. 先用履约和评价治理保护收入和体验。
2. 再用卖家分层提升供给质量。
3. 最后用客户召回和复购实验提升客户价值。

这个顺序比同时铺开所有运营动作更可控，也更符合当前数据能支持的证据强度。

# 附录 B：Power BI 页面逐项使用说明

## B.1 经营总览

用途：给管理层看整体经营是否健康。

使用顺序：

1. 先看 GMV、成交订单量、客单价，判断规模。
2. 再看复购客户率，判断客户是否留下。
3. 最后看延迟率、差评率，判断体验风险。
4. 用下单月份和客户州切片器定位异常。

常见解释：

- GMV 上升但客单价下降，说明增长主要来自订单量。
- 订单量正常但延迟率上升，说明供给或物流出现问题。
- 差评率与延迟率同步上升，优先排查履约。

## B.2 类目与地区

用途：判断收入集中度和区域/类目风险。

使用顺序：

1. 看类目 GMV 排名，确认头部类目。
2. 看类目延迟率和差评率，选择风险类目。
3. 看地区商品金额，确定重点区域。
4. 交叉检查地区 × 类目矩阵。

## B.3 履约与评价

用途：定位延迟从哪个阶段产生，以及差评何时跳升。

使用顺序：

1. 看平均履约天数、延迟率、差评率。
2. 用月度趋势确认是否持续恶化。
3. 对比准时和延迟订单的处理/配送时间。
4. 对延迟超过 4 天的订单建专项跟进。

## B.4 客户经营

用途：判断复购和客户价值。

使用顺序：

1. 先看复购客户率和复购客户数。
2. 再看客户平均消费。
3. 关注高消费待激活人群。
4. 以 28 天和 80 天为召回测试窗口。

## B.5 卖家风险

用途：找到大而差的卖家，安排抽查和整改。

使用顺序：

1. 先看风险卖家数和风险卖家 GMV。
2. 选择风险层级和风险原因。
3. 对高 GMV、高延迟或高差评卖家排序。
4. 建立 30 天整改台账。

# 附录 C：异常诊断 SOP

## C.1 GMV 异常

可能原因：

- 订单状态变化，已送达订单减少。
- 某类目或头部卖家下架。
- 促销结束后需求回落。
- 数据刷新失败或日期范围不完整。

检查步骤：

1. 比较支付金额 GMV 与商品金额加运费。
2. 检查 GMV 最大的州和类目。
3. 检查订单量和客单价是否同步变化。
4. 检查最后一天数据是否完整。

## C.2 延迟率异常

可能原因：

- 某地区运输受阻。
- 某卖家处理变慢。
- 预计送达时间设置过紧。
- 大促导致订单集中。

检查步骤：

1. 先按州拆分延迟率。
2. 再按卖家和承运阶段拆分。
3. 比较卖家处理天数和运输配送天数。
4. 看订单量，区分高比例风险和高绝对影响。

## C.3 差评率异常

可能原因：

- 延迟超过 4 天。
- 商品破损或描述不符。
- 某类目包装问题。
- 某卖家质量下降。

检查步骤：

1. 先看是否集中在一个类目。
2. 再看是否集中在一个卖家。
3. 对延迟区间做交叉。
4. 抽取差评订单原文或评价时间做人工复核。

# 附录 I：SQL 实现逻辑摘要

## I.1 成交订单过滤

订单分析视图的核心过滤条件是 `order_status = delivered`。所有成交类指标都应从该范围开始，避免后续不同页面口径漂移。

## I.2 支付金额聚合

支付表一个订单可能有多笔记录，因此先按 order_id 汇总 payment_value，再与订单表连接。不能直接多表连接后求和，否则订单金额会被商品行放大。

## I.3 商品和运费聚合

商品表先按 order_id 汇总商品行数、商品价格、运费和商品金额加运费，再与订单表连接。

## I.4 评价聚合

同一订单可能有多条评价，因此：

- review_count 记录评价条数。
- avg_review_score 先按订单取平均。
- min_review_score 用于判断差评。
- bad_review_order 定义为最低评分 <= 2。

## I.5 履约日期计算

| 指标 | SQL 逻辑 |
|---|---|
| approval_days | approved_at - purchase_timestamp |
| seller_handling_days | delivered_carrier_date - approved_at |
| carrier_delivery_days | delivered_customer_date - delivered_carrier_date |
| total_delivery_days | delivered_customer_date - purchase_timestamp |
| is_late | delivered_customer_date > estimated_delivery_date |

## I.6 客户复购

按 customer_unique_id 聚合 delivered 订单数。订单数 >= 2 的客户为复购客户。最后用复购客户数除以全部成交客户数。

## I.7 类目风险聚合

类目分析必须先按 category_name + order_id 聚合类目订单金额，避免同一订单多个商品行重复计入订单。延迟率和差评率则在订单级做布尔标记后聚合。

## I.8 卖家风险聚合

卖家订单先按 seller_id + order_id 聚合，再连接订单级履约和评价标记。若要计算卖家销售额，商品金额按卖家订单汇总；若要计算订单量，必须对 order_id 去重。

## K.3 客户召回实验

实验目标：提升高消费待激活客户的二购率。

实验对象：RFM 高消费待激活且最近一次购买在 180 天内的客户。

实验组与控制组：

- 实验组 A：28 天提醒。
- 实验组 B：28 天提醒 + 品类推荐。
- 实验组 C：80 天提醒 + 小额优惠。
- 控制组：不触达。

核心指标：

# 附录 M：常见故障排查

## M.1 MySQL 导入

- 首行丢失：检查 LINES TERMINATED BY 和 ESCAPED BY。
- 经纬度精度丢失：检查字段是否为 DOUBLE。
- 中文乱码：统一 utf8mb4。
- 本地文件导入失败：确认 local_infile 已临时开启。

## M.2 Power BI 关系

- 订单量重复：检查是否存在一对多连接后计数。
- 复购率异常：检查是否使用 customer_unique_id。
- 日期关系异常：检查事实表日期与本地日期表关系。
- 类目金额不一致：检查是否先聚合到订单再归属类目。

## M.3 PBIP/PBIX

- PBIP 页面 JSON 语法错误：逐页检查 visual.json。
- 卡片副标题不支持 color：移除非法属性。
- 切片器筛选异常：优先使用原生切片器选择状态，不手写复杂 filterConfig。
- PBIX 损坏：不要反复覆盖原文件，先保留备份并从 PBIP 重新另存。
